# Gateway-owned groups in Desktop

A Group Chat is either a **gateway room** (the gateway owns its log and runs its turns; `canonical-group*` in `src/plugins/hermes-bots/`) or a **classic room** (Desktop runs its rounds; `group-*`). Opening a gateway room captures its exact authority (connection, profile, room id); changing the foreground profile does not retarget its controls.

## Which rooms are gateway rooms

One classifier, `groupExecutionMode`, reads `groups.capabilities`. The gateway (`gateway/session_group_controls.py`) answers directly or through the server used by remote connections (`tui_gateway/methods_groups.py`); a standalone server may instead own its own rooms.

- **Gateway rooms:** an answer with `driver: true`, from either surface. Both run their own room driver, so these rooms keep working while Desktop is closed. An answer without a running driver is unavailable (below), but a room Desktop has already bound (opened from the gateway list, or earlier in this session) still opens and says its group driver is unavailable.
- **Classic rooms through the migration gate:** only a server that reports no room driver and owns no rooms (`driver: false`, `persistent_process: false`), as on `main`. Desktop runs those rooms itself; no other capability answer makes the gate fall back to it. A room already routed to a Desktop-driven workspace does not enter this gate.
- Anything else is unavailable, and the gate says why and offers **Retry**: a server without the group surface (`-32601`) or with an answer Desktop can't read is too old for group chats (update Hermes on that computer and reconnect); an answer whose driver isn't running asks to restart or update Hermes there; a transport error, or a socket that isn't open, could not reach the gateway.

A gateway room offers a control only when the answer's `methods` lists its method: Discard (`groups.discard`), Retry (`groups.retry`), Allow and Deny (`groups.approve`), file upload and download, including pasted or dropped files and inline image previews (`groups.attachment.upload`, `groups.attachment.download`), Rename (`groups.rename`) and Disband (`groups.disband`). Current standalone servers support attachments. A standalone-owned room does not advertise `groups.discard`; when a gateway owns the room, the standalone server forwards its room methods and advertises the methods the owner offers. Older standalone servers without attachment methods still hide upload and disable **Download**. For a room on the foreground connection, the list holds for one opening of that gateway socket: an update restarts the gateway, so when the socket reopens the list is read again, and a reply that started before the socket changed is dropped. Until a read for the current opening succeeds none of these controls is offered, and a failed read is tried again every two seconds while the room is visible; a successful answer without a method list keeps them all. A room on another connection retains its own list until reopened; changes to the foreground socket do not invalidate it.

New Group Chat retains the union picker, device badges and `seatableGroupBots` rules. `groupCreationEngine` is the single decision point: same-connection members use `gateway`; a mixed selection uses `gateway-peer` only when its owner advertises a persistent driver and `groups.peer.register`, and every lender qualifies. The owner need not enable its own RoomLink endpoint. Each other member must route consistently to its gateway's default profile, whose successful capabilities read advertises `groups.peer.invite` and an enabled, compatible text-only persistent catalog with matching installation identity and an endpoint. Pending checks disable Create; an unavailable owner or invalid route also disables it. Missing peer roles retain the Desktop courier and its lifetime note. Bots all on one other connection keep the switch-connection guidance. The complete plan is read again before creation.

Gateway records extend the existing `engine` field with `{kind: 'gateway', connectionId, profile, roomId}`. This local owner record survives storage, hydration, membership edits and rename; name reopening checks its complete identity before accepting a cached binding. A canonical key opens its own connection, profile and room id. Other Desktops discover gateway rooms through `groups.list`; these owner records are not published through the ui_meta mirror. A mirrored Desktop room with a conflicting identity leaves the local gateway record unchanged. Confirmed Disband retires the matching local owner record so its name can be reused. Losing a peer never changes the engine. Unmarked mixed records from unreleased earlier builds are not migrated. Existing Desktop-driven mixed rooms stay usable and, when the same plan permits it, offer **Start new gateway group**: a separate room with the same Bots, leaving earlier history in the Desktop room.

## Bots on other gateways

Desktop creates the room on its owner, invites each peer on its own gateway, then registers the pinned catalog, endpoint and grant on the owner. Grants remain transient in Desktop. Once created, a gateway room is never replaced by a courier fallback: interrupted setup leaves the same room with an unjoined member. The current header shows **hasn't joined**, **Retry**, and **Start new group without X** (a separate room, followed by ending the original when confirmed). Two Desktops confirming replacement simultaneously can each create a new room; replacement is not coordinated across Desktops. This is separate from the driver's preparation-stall Retry. Retry finds a connection matching the pinned installation and catalog; ordinary failures never revoke a working scope. Connection kind (SSH, URL or otherwise) is not an eligibility rule; advertised capabilities are.

Invitations allow dispatch for one day and request a 30-day renewal horizon only when advertised. While a room is open, Desktop re-seats joined peers after 20 hours or on the first open after restart; failed attempts retry after five minutes, and a newly loaded connection retries immediately. A Send is journaled before waiting up to 45 seconds for renewal, and Stop still holds that Send back. The owner can renew on dispatch only while the current grant remains dispatch-valid. There is no Desktop background renewal loop: after more than a day idle, open the room with a reachable lender or use Retry. Re-seating does not revoke earlier grants; they expire or are covered by the gateway's scope revocation. Peer turns take text only, require the lender's default profile, and require the advertised endpoint to be reachable from the owner.

A classic room that reaches `GroupExecutionGate` on a gateway connection is first looked up by name in `groups.list`; a match opens that gateway room. Otherwise the gate says what happened, why, what to do and what happens to the earlier messages. These rules apply to rooms that reach the gate, not to rooms already routed to a Desktop-driven workspace.

- Bots that can form a gateway group on this connection: the gate offers **Start new group**, a fresh gateway room with the same Bots that keeps working when Desktop is closed. Earlier messages are not copied into it.
- Bots on other connections, or on several (some here, some elsewhere): the gate names those connections and says to switch to the connection where the Bots run and start a group there, or to start a new group chat with Bots from this connection.
- Bots here that cannot form a gateway group as they are (two to six Bots, distinct profiles and handles, `@all` and `@everyone` reserved): the gate gives the reason and says to start a new group chat and choose its Bots.
- A failed lookup offers **Retry**.

Under the gate, a classic room's earlier messages stay readable, read only and inert, like gateway room history below: no `MEDIA:` path, Markdown image, file link or directive card resolves, rich fences show their source, and only an explicit web link to a public host opens, on a click. They stay on this Desktop.

## The room workspace

The gateway owns the log and the work. Desktop polls `groups.state` and `groups.log` every two seconds while the room is visible. It reads the log after the last event it showed, and from the start again when the room's `authority_epoch` changes.

- **Status:** the header lists each member as working or queued (`driver_status.member_activity`) and, beside that, what the room waits on: a blocked room (a stopped task that is still settling is not a block), approvals, and other pending actions. A gateway whose driver is down sends no driver status; the room then says its group driver is unavailable. A failed member never hides the others' live work.
- **Send** uses the native prepared-submission journal: one unresolved intent per room, shared by every Desktop window and written with compare-and-set. The entry counts the requests that may have posted its intent: one more is written before each request leaves, one less when the gateway proves that request posted nothing. Both gateway surfaces give that proof by marking a refusal `admitted: false` (on `4001`, `4111`, `4123` or `5112`), and only for a refusal raised before the user event commits or a Send no driver or worker could take; a code or reason alone proves nothing. Main already returns the committed event when preparing the room fails afterwards, and its driver reports persistent preparation failure with Retry; this PR preserves that recovery. At zero the words come back for editing, and the journal keeps them until a Send replaces them, so a room closed meanwhile shows them again when it reopens. Any other outcome (an unmarked refusal, a timeout, an unconfirmed reply) keeps the intent for **Retry**, which resends the same `event_id`; the gateway recognizes it, so it is never posted twice. A Send is delivered only by a receipt whose `client_event_id` is this intent's (and `accepted: true` when present); a failed journal cleanup after that receipt is retried before this window's next Send. When another window holds the room's intent, Send sends that one first and puts this window's words back afterwards; an intent another window finished with is neither resent nor offered as a new message. If the journal cannot be read, Send stays locked and **Try loading again** reads it again without writing.
- **Stop** (`groups.stop`) has its own pending state, so it works while a Send is in flight. It keeps one `cancel_id` until the gateway confirms how many replies it stopped. Stop also covers a Send in flight: one not yet sent is held back with its words kept; one on the wire is fenced again under a fresh `cancel_id` once it settles, unless the gateway proved it posted nothing.
- **Retry, Discard and approvals** come only from `driver_status.pending_actions` and send the exact member, task, generation and request identity. Each row names its Bot. An approval shows its description and its command; only the choices the gateway offered appear, and **Allow once** needs this exact request with a real command, or with the description a synthetic tool label stands for (a plugin approval rule sends `<tool> (plugin approval rule)`, as in the chat approval card). Discard asks first: side effects are not undone.
- **Attachments** upload with `groups.attachment.upload` and download with `groups.attachment.download`.
- **Rename** (`groups.rename`) sends the trimmed new name from the room header. **Disband** (`groups.disband`) asks through a confirmation dialog, which stays open with the error when the gateway refuses; once the gateway confirms, Desktop leaves the room, drops it from the sidebar and its bindings, and says it was disbanded.

History shows messages and notices for failed, cancelled and deferred turns (a deferred turn names its reason, such as `member_unavailable`), a stop, the work limit (`room.activity` with status `bounded`), the room's end and lost ownership; every other event (`turn.started`, `turn.settled`, other `room.activity`, …) stays out. Your own messages read as **You**. Room text may come from another machine: its `MEDIA:` paths, Markdown images, file links and directive cards stay inert, rich code fences (`listing`, `mermaid`, `svg`) show their source, and an explicit web link to a public host (not loopback, link-local or a private network) opens only on a click.

Errors stay visible, and no failed gateway-room action falls back to Desktop-run execution. Membership editing is not offered.

## Contract tests

`canonical-group-contract-test-utils.ts` wraps each canonical group test's request double and, after each test, checks every `groups.*` request it captured against the generated gateway contract (`apps/shared/src/gateway-contract.openrpc.json`, the gateway's own `x-canonical-methods` entry before the shared one): a method the gateway does not list, an unknown parameter or a missing required one fails the test. The `groups.capabilities` fixtures for both surfaces are data, checked against the same contract when they load. `canonical-groups-contract.test.ts` covers the check itself.
